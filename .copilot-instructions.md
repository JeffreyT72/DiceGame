# Copilot Instructions

## Project overview

This is a JavaScript ES-module game. The browser client uses Phaser for the blackjack table and plain HTML/CSS/JavaScript for menus and other screens. The Node.js server uses Express, SQLite, and WebSockets. Gameplay definitions and rules are shared between the client and server where practical.

## Where to make changes

- `client/index.html`, `client/src/ui/`, and `client/src/styles/` contain the screen markup, UI behavior, and styling. Keep DOM selectors and element IDs synchronized between markup and scripts.
- `client/src/game/` contains Phaser scenes and client-side combat presentation.
- `client/src/services/api.js` and `client/src/services/multiplayer.js` are the HTTP and WebSocket client boundaries.
- `server/server.js` contains HTTP routes, account/session handling, and SQLite setup. `server/blackjack.js` owns blackjack hand rules; `server/multiplayer.js` owns in-memory multiplayer rooms.
- `shared/` contains gameplay rules and configuration used across layers. Keep server-side validation and outcome resolution authoritative; update client presentation and tests when shared rules change.
- Single-player and multiplayer dungeon definitions are intentionally separate in `shared/dungeon-config.js` and `shared/dungeon-multiplayer-config.js`.

## Conventions and verification

- Follow the surrounding JavaScript style and existing module boundaries; do not add dependencies for small changes.
- Add or update tests alongside the behavior being changed. Tests use `node:test` and are named `*.test.js`.
- Run `npm test` for the test suite and `npm run build` for the production frontend build. `npm run dev` starts the client and server together.
- There is no lint script in `package.json`; do not claim that linting was run unless you invoke a linter directly.
- Update `README.md` when setup, deployment, gameplay, or configuration behavior changes.

## Data safety

Runtime SQLite files under `data/` contain player accounts and game state. Do not edit, delete, or replace them as part of ordinary code changes, and do not add database files or secrets to commits. Preserve existing user data when changing database schemas or persistence behavior.
